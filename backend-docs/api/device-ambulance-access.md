# Устройства скорой, машины и доступ устройства

[К общей документации API](../API_DOCUMENTATION.md)

По типу клиента: [веб — управление планшетами и машинами](../API_WEB_CLIENT.md),
[мобильное приложение — вход и смена](../API_MOBILE_AMBULANCE.md).

Этот раздел описывает два независимых сценария:

1. Администратор создаёт запись машины и один раз выдаёт физическому планшету пару `device_id` + `auth_secret`.
2. Планшет в начале смены выбирает машину, получает токены и затем поддерживает сессию через refresh-токен.

Базовый URL: `http://localhost:<BACKEND_PORT>/api/v1`. Все тела запросов — JSON с заголовком `Content-Type: application/json`.

Успешный ответ с телом имеет обёртку `data`; ошибка — `message`:

```json
{
  "message": "invalid request body"
}
```

Административные ручки защищены user access token и правами роли. Для
provisioning нужен `device.provision`, для просмотра устройств — `device.read`,
для смены секрета — `device.reset_secret`, для отключения планшета —
`device.change_status`, а управление машинами требует
`ambulance_vehicle.manage`. Порядок seed и создания первого администратора
описан в [RBAC](../RBAC.md).

## Модель данных и безопасность

- `device` — постоянный, обезличенный физический планшет, не пользователь и не машина.
- `ambulance_vehicle` — справочник машин. Одна активная сессия может занимать одну машину.
- `device_access_session` — временная привязка планшета к машине на смену. Одновременно у устройства и у машины может быть только одна активная сессия.
- `auth_secret` создаётся сервером, хранится на планшете в защищённом хранилище и передаётся только при `device-access/login`. В БД хранится только bcrypt-хеш.
- Секрет возвращается только при provisioning и сбросе. Сохранить его нужно сразу: последующие GET-запросы его не вернут. Все ответы с секретом или токенами содержат `Cache-Control: no-store`.
- Сброс секрета отзывает активную сессию устройства на уровне БД.
- Отключение устройства отзывает активную смену; middleware проверяет действительность смены и статус устройства в БД на каждом запросе, поэтому прежний access-токен сразу перестаёт работать.
- Отключение планшета отзывает его активную смену. На каждом защищённом запросе сервер проверяет в БД статус устройства и смены, поэтому старый access-токен перестаёт работать сразу.

`device` access-токен уже защищает ручки [запуска и отмены прохождения чеклиста](checklist-runs.md). Не используйте токен устройства как токен сотрудника.

## Рекомендуемый поток для фронтенда

```text
Администратор: POST /ambulance-vehicles/ → POST /device/
                                             ↓ один раз передать планшету
Планшет: POST /device-access/login → access_token + refresh_token
                                             ↓
                               POST /device-access/refresh
                                             ↓
                               POST /device-access/logout
```

Номер машины при входе нормализуется сервером: пробелы по краям отбрасываются, буквы переводятся в верхний регистр. Пример: ` a123bc77 ` → `A123BC77`.

## Машины скорой

### POST /api/v1/ambulance-vehicles/

Создаёт машину. Номер должен быть уникальным; статус новой машины — `active`.

```json
{
  "car_number": "A123BC77"
}
```

Ответ: `201 Created`.

```json
{
  "data": {
    "id": "7f8e972f-207a-4c37-b6cf-87757b224c7c",
    "car_number": "A123BC77",
    "status": "active",
    "created_at": "2026-09-18T10:00:00Z",
    "updated_at": "2026-09-18T10:00:00Z"
  }
}
```

Ошибки: `400` — пустой/некорректный JSON или номер; `409` — такой номер уже есть.

### GET /api/v1/ambulance-vehicles/

Возвращает все машины, отсортированные по номеру.

Ответ: `200 OK`, `data` — массив объектов машины из примера выше. Пустой список: `{"data":[]}`.

### GET /api/v1/ambulance-vehicles/{id}

Возвращает машину по UUID.

Ответ: `200 OK`, `data` — объект машины. Ошибки: `400` — некорректный UUID; `404` — машина не найдена.

### PATCH /api/v1/ambulance-vehicles/{id}

Частично изменяет номер и/или статус. Нужно передать хотя бы одно поле. Допустимые статусы: `active`, `inactive`, `maintenance`.

```json
{
  "status": "maintenance"
}
```

```json
{
  "car_number": "B456CC77",
  "status": "active"
}
```

Ответ: `200 OK`, объект машины в `data`.

Ошибки: `400` — пустой объект, неверный UUID/статус/номер; `404` — машина не найдена; `409` — новый номер занят или машина участвует в активной сессии устройства. Во время активной сессии нельзя изменить номер машины или перевести её в `inactive`/`maintenance`.

Удаления машины нет: это намеренно сохраняет историю смен.

## Provisioning устройства

### POST /api/v1/device/

Сервер создаёт новую запись устройства и генерирует оба credential: `device_id` и `auth_secret`. Тело запроса не требуется.

Ответ: `201 Created`, заголовок `Cache-Control: no-store`.

```json
{
  "data": {
    "device": {
      "id": "46a34243-0647-40fe-8e30-222c2f36d534",
      "device_id": "1fdaee6a-d2cd-4b8f-a0a0-0c5fd8542a0f",
      "status": "active",
      "created_at": "2026-09-18T10:01:00Z",
      "updated_at": "2026-09-18T10:01:00Z"
    },
    "auth_secret": "SECRET_VALUE_RETURNED_ONCE",
    "qr_payload": "{\"type\":\"vera.device.provisioning\",\"version\":1,\"device_id\":\"1fdaee6a-d2cd-4b8f-a0a0-0c5fd8542a0f\",\"auth_secret\":\"SECRET_VALUE_RETURNED_ONCE\"}"
  }
}
```

Веб-клиент кодирует **строку** `data.qr_payload` в QR-код без изменения её содержимого. Мобильное приложение считывает JSON из QR, проверяет `type` и `version`, сохраняет `device_id` и `auth_secret` в защищённом хранилище; номер машины вводится отдельно при начале смены. `auth_secret_hash` — bcrypt-хеш только в БД: передавать его планшету нельзя, с ним вход не сработает. Не логируйте QR и секрет, не помещайте их в URL и не сохраняйте изображение QR после выдачи.

QR и секрет доступны только в этом ответе и при сбросе секрета. `GET /device/` и `GET /device/{device_id}` не возвращают их. Если ответ потерян, нужен сброс секрета, а не повторный GET.

### GET /api/v1/device/

Возвращает список устройств.

Ответ: `200 OK`, `data` — массив:

```json
{
  "data": [
    {
      "id": "46a34243-0647-40fe-8e30-222c2f36d534",
      "device_id": "1fdaee6a-d2cd-4b8f-a0a0-0c5fd8542a0f",
      "status": "active",
      "last_seen_at": "2026-09-18T10:12:00Z",
      "created_at": "2026-09-18T10:01:00Z",
      "updated_at": "2026-09-18T10:01:00Z"
    }
  ]
}
```

`last_seen_at` отсутствует, пока сервер не реализовал приём геопозиции/heartbeat. Секрет и его хеш никогда не возвращаются.

### GET /api/v1/device/{device_id}

Возвращает устройство по внешнему `device_id`, а не по UUID записи.

Ответ: `200 OK`, `data` — объект устройства. Ошибки: `400` — пустой идентификатор; `404` — устройство не найдено.

### PATCH /api/v1/device/{device_id}/status

Отключает потерянный или списанный планшет. Требуется employee JWT с правом `device.change_status`. Чтобы соответствовать текущему запросу веб-клиента, тело принимает `inactive`; сервер сохраняет и возвращает статус `disabled`, как определено схемой БД.

```json
{"status":"inactive"}
```

Ответ: `200 OK`, объект устройства в `data` со статусом `disabled`. Активные смены отзываются, поэтому access- и refresh-токены планшета больше не действуют. Изменение, отзыв смен и запись аудита выполняются атомарно. Повторное отключение возвращает тот же статус без повторного события аудита. Для повторного ввода устройства в работу этой ручки недостаточно: сначала потребуется отдельный безопасный сценарий.

Ошибки: `400` — пустой device_id или неподдерживаемый статус; `404` — устройство не найдено; `401`/`403` — нет токена или права.

### DELETE /api/v1/device/{device_id}

Логически удаляет устройство. Требуется employee JWT с правом `device.delete`; `device_id` — внешний идентификатор планшета.

Ответ: `204 No Content`. Запись остаётся в БД для истории, но исключается из списков, поиска и аутентификации. Устройство переводится в `disabled`, его активные смены отзываются, а событие записывается в аудит атомарно. Повторный DELETE вернёт `404`.

Ошибки: `400` — пустой device_id; `404` — устройство уже удалено или не найдено; `401`/`403` — нет токена или права.

### POST /api/v1/device/{device_id}/auth-secret

Администратор заменяет секрет устройства. Тело не требуется.

Ответ: `200 OK`, формат совпадает с provisioning, включая новый `qr_payload`; заголовок `Cache-Control: no-store`.

Новый `auth_secret` выдаётся один раз. После сброса все активные смены этого устройства отзываются и планшет должен пройти вход заново с новым секретом.

Ошибки: `400` — пустой идентификатор; `404` — устройство не найдено.

## Вход устройства и управление сменой

### POST /api/v1/device-access/login

Открывает смену: проверяет секрет устройства и активную машину, создаёт `device_access_session`, возвращает пару JWT.

```json
{
  "device_id": "1fdaee6a-d2cd-4b8f-a0a0-0c5fd8542a0f",
  "auth_secret": "SECRET_VALUE_FROM_SECURE_STORAGE",
  "car_number": "A123BC77"
}
```

Ответ: `200 OK`, заголовок `Cache-Control: no-store`.

```json
{
  "data": {
    "access_token": "DEVICE_ACCESS_JWT",
    "refresh_token": "DEVICE_REFRESH_JWT",
    "expires_at": "2026-09-18T22:15:00Z"
  }
}
```

`expires_at` — окончание смены. Access-токен может иметь более короткий срок жизни, заданный `JWT_ACCESS_TTL`; для продления используйте refresh-токен. Не показывайте и не логируйте оба токена.

Ошибки:

- `400` — отсутствует обязательное поле, некорректный JSON или есть неизвестное поле;
- `401` с `invalid device credentials or session` — неверный/несуществующий `device_id`, секрет или токен;
- `403` — устройство отключено;
- `404` — машины с таким номером нет;
- `409` — машина не `active`, у устройства уже есть смена или машина уже занята другим устройством.

### POST /api/v1/device-access/refresh

Заменяет пару токенов, не продлевая саму смену: `expires_at` остаётся прежним. Новый refresh-токен заменяет старый — сохранить надо именно новый.

```json
{
  "refresh_token": "DEVICE_REFRESH_JWT"
}
```

Ответ: `200 OK`, формат совпадает с ответом login, `Cache-Control: no-store`.

Ошибки: `400` — некорректное тело; `401` — токен недействителен, уже заменён, смена отозвана или истекла.

### POST /api/v1/device-access/logout

Завершает смену и отзывает текущий refresh-токен.

```json
{
  "refresh_token": "DEVICE_REFRESH_JWT"
}
```

Ответ: `204 No Content`, тела нет. Повторный logout или последующий refresh с тем же токеном вернёт `401`.

## Хранение токенов на клиенте

- `auth_secret` — долгоживущий credential: только защищённое системное хранилище планшета.
- `access_token` — отправляется как `Authorization: Bearer <token>` на будущих защищённых ручках устройства.
- `refresh_token` — только защищённое хранилище; при каждом успешном refresh заменяется новым значением.
- Не хранить значения в URL, аналитике, логах приложения, localStorage браузера или обычных настройках приложения.
