# Демо-данные для локального тестирования

`seed-demo` создаёт **синтетический**, связанный набор данных в уже мигрированной
базе через те же сервисы, что используют API: планшет выдаётся через
`ProvisionDevice`, чеклист собирается как `draft` и публикуется через
`PublishChecklistVersion` с аудитом. Команда запускается вручную и не входит в
автоматический запуск API.
Перед первым запуском необходимо выполнить миграции. Для реальных медицинских
данных и production эту команду не использовать.

Локальный запуск из корня репозитория (при настроенном `DATABASE_URL` в `.env`):

```sh
go run ./cmd/seed-demo -allow-demo-data
```

Если база и API запущены через Docker Compose, дождитесь завершения `migrate`
и `rbac-seed`. После добавления команды seed пересоберите образ, чтобы в нём
появился `/seed-demo`:

```sh
docker compose build server
docker compose run --rm --no-deps --entrypoint /seed-demo server -allow-demo-data
```

В **Git Bash на Windows** используйте вместо второй строки команду ниже.
Иначе Git Bash может заменить Linux-путь `/seed-demo` на путь вроде
`D:/Git/seed-demo`, и контейнер не запустится:

```sh
MSYS_NO_PATHCONV=1 docker compose run --rm --no-deps --entrypoint /seed-demo server -allow-demo-data
```

В PowerShell исходная команда работает без `MSYS_NO_PATHCONV`.

База для контейнера берётся из `DATABASE_URL_DOCKER`. Сначала проверьте, что
этот URL указывает именно на локальную/тестовую БД. Команда сама создаёт
недостающие RBAC-права, но **не создаёт администратора**; первый администратор
по-прежнему создаётся штатным `rbac-seed`.

Что появится:

- машина `DEMO002` и планшет с **сгенерированным сервисом** `device_id` и секретом;
- демо-сотрудник больницы `demo_hospital_staff_v2` с ролью, минимальными правами
  на просмотр больницы, статусов ресурсов и прибытия, а также назначением в неё;
- тип учреждения, Оренбургская областная клиническая больница им. В.И. Войнова
  (`460024, г. Оренбург, ул. Аксакова, 23`, телефон приёмной главного врача
  `+7 (3532) 31-47-22`), категория случая и связь больницы с ней;
- координата больницы приблизительная — точка на территории, **не проверенный
  въезд для скорой** ([источник точки на территории](https://sobory.ru/article/?object=32568)).
  Зона обслуживания вокруг неё целиком учебная и **не**
  соответствует реальной территории ответственности больницы;
- тип оборудования, экземпляр оборудования, тип операционной и операционная
  со статусом `available`;
- опубликованный чеклист «DEMO v2 — осмотр бригады» с вопросами типов `single`,
  `multiple`, `text`, `number`, `boolean`; у обязательного `single` есть ответы
  «Да»/«Нет», у `multiple` — два варианта;
- два результата, правило для «Да» и fallback-правило для остальных ответов;
  оба результата направляют в демо-больницу; результат «Да» также требует
  доступное оборудование и операционную.

На первом запуске команда напечатает `auth_secret` планшета и пароль сотрудника.
Сохраните их в защищённом месте: повторный запуск **не** показывает и **не**
сбрасывает существующие секреты. Не добавляйте вывод команды в Git, общий чат
или журналы CI. Если секрет потерян, используйте штатный сброс через API
администратора.

Для проверки мобильного сценария:

1. `POST /api/v1/device-access/login` с JSON
   `{"device_id":"<device_id из вывода seed>","auth_secret":"<секрет из вывода>","car_number":"DEMO002"}`.
2. С выданным `access_token`: `GET /api/v1/device/checklists` — в списке будет
   «DEMO v2 — осмотр бригады». ID чеклиста и опубликованной версии выводятся командой.
3. Создайте вызов, пройдите чеклист и сохраните ответ на обязательный вопрос.
   Его ID и ID вариантов «Да»/«Нет» также выводятся командой. `complete` вернёт
   соответствующий результат. Рабочие маршруты и тела запросов приведены в
   [мобильной API-документации](API_MOBILE_AMBULANCE.md).

Для входа демо-сотрудника: `POST /api/v1/auth/login` с
`{"user_name":"demo_hospital_staff_v2","password":"<пароль из вывода>","device_id":"demo-web"}`.

Повторный запуск не создаёт дубли и не перезаписывает отредактированные
демо-объекты: команда хранит выданные сервисами ID в локальной таблице
`demo_seed_state`. Это технический реестр сида, не бизнес-данные.
Если вы архивировали демо-версию, отключили устройство или
сотрудника, повторный seed **не** вернёт их в исходное состояние — используйте
соответствующие API или новую тестовую базу. Транзакционные данные (смены,
вызовы, заполненные ответы, GPS) намеренно не создаются: они должны возникать
при прохождении сценария, а не храниться как статический справочник.

Старые данные, созданные прежним сидом прямыми SQL-вставками (`DEMO001`,
`demo-tablet-001`, старый чеклист), **не удаляются и не переиспользуются**.
Новый сид создаёт набор `v2` через сервисы; больница с указанным названием
переиспользуется, если уже существует и её адрес совпадает. Если ранее
созданная больница имеет другой адрес, сид остановится, не перезаписав её.
Для удаления устаревших демо-записей сначала проверьте связи и исторические
данные; автоматического удаления в сиде нет.

Почтовый индекс `460024` указан для демонстрации по входным данным проекта.
Перед использованием справочника для реальной маршрутизации адрес нужно
проверить: [реестр ОМС Оренбургской области](https://www.orenfoms.ru/reestry/reestr-mo/)
указывает для этой организации индекс `460018`. Точку въезда и официальную
зону обслуживания тоже необходимо подтверждать отдельно.
