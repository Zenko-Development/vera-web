# Дорожная карта развития Vera Backend

Этот документ отделяет уже работающий MVP-сценарий от следующих задач. Порядок
важен: сначала завершаем полезный для бригады и больницы функционал, затем
усиливаем эксплуатационную и security-часть.

## Текущий MVP

Уже реализованы следующие части основного сценария:

```text
device + машина + смена
    -> emergency call + GPS-точки
    -> checklist run + ответы
    -> Rule Engine + checklist result
    -> выбор больницы: fixed / by_tag / by_service_area
    -> сохранённое назначение больницы
```

Администратор может создавать сотрудников, роли и права, чеклисты и их
опубликованные версии, устройства, машины, больницы и зоны обслуживания.
Реализованы справочники оборудования и операционных, физические ресурсы
больницы, назначения сотрудников и изменение состояния ресурсов с проверкой
RBAC и принадлежности сотрудника больнице.

## Ресурсы больницы

Пункты 1–4 реализованы в миграциях `028_hospital_resources`,
`029_checklist_result_resource_requirements` и модулях
`internal/hospital_resource`, `internal/checklist_result_requirement`.

### 1. Справочники ресурсов — реализовано

Создать два общесистемных справочника:

- `equipment` — тип оборудования, например КТ, аппарат ИВЛ или ангиограф;
- `operating` — тип операционной или её профиль.

Они описывают **что бывает в системе**, но не наличие ресурса у конкретной
больницы.

### 2. Ресурсы конкретной больницы — реализовано

Добавить сущности `hospital_equipment` и `hospital_operating`.

Каждая запись должна содержать связь с больницей, тип ресурса, статус,
время последнего изменения и, при необходимости, понятный номер/название.
Минимальный набор статусов для MVP:

- `available` — ресурс можно использовать;
- `busy` — ресурс занят;
- `unavailable` — неисправен, закрыт или временно недоступен.

Не следует удалять ресурс при временной недоступности: история статуса важнее
удаления строки.

### 3. Работа сотрудника больницы — реализовано

Нужны CRUD-ручки для администратора и ограниченные ручки состояния для
сотрудника больницы. Перед включением ограничения «только своя больница»
необходимо добавить явную связь сотрудника с больницей. Иначе сервер не сможет
надёжно определить, какую больницу разрешено изменять.

Критерий готовности: сотрудник меняет статус конкретной операционной или
единицы оборудования, а API возвращает `updated_at` и новое состояние.

### 4. Учёт ресурсов при направлении бригады — реализовано

После того как статусы станут надёжными, расширить routing:

1. чеклистный результат определяет медицинские требования — теги, профиль,
   оборудование или операционную;
2. routing находит кандидатов по текущей геозоне/правилу;
3. из кандидатов исключаются больницы без требуемых доступных ресурсов;
4. список кандидатов и итоговый выбор сохраняются в emergency call как
   исторический снимок.

Если подходящих больниц нет, результатом должен быть явный `no_candidates`, а
не произвольная больница.

## Развитие зон обслуживания и импорт картографических данных

Таблица `hospital_service_area` уже является источником истины для фактической
зоны ответственности больницы. Во время вызова routing должен использовать
только сохранённые в нашей БД полигоны и последнюю GPS-точку вызова — без
внешнего HTTP-запроса к картографическому провайдеру.

### Импорт административных границ

OpenStreetMap/Nominatim/Overpass можно добавить как вспомогательный инструмент
администратора:

```text
название района или OSM relation id
    -> получение и предпросмотр геометрии
    -> ручное подтверждение администратора
    -> сохранение hospital_service_area.boundary
```

- Nominatim может помочь найти объект по названию, но `boundingbox` — только
  прямоугольник вокруг района, а не точная зона для routing;
- Overpass/GeoJSON могут быть источником полного контура;
- импортированная административная граница не должна автоматически становиться
  зоной больницы: фактические зоны ответственности могут отличаться;
- публичные OSM-сервисы не вызываются в критическом пути вызова и не получают
  данные пациента или текущие координаты бригады.

Для MVP допустим один простой замкнутый полигон в одной service area. Сложный
район можно задать несколькими зонами одной больницы. Когда понадобится
поддержка multipolygon и "дыр" внутри территории, заменить формат `boundary`
на GeoJSON `MultiPolygon` или геометрию PostGIS и добавить проверку импорта.

Вместе с импортом добавить метаданные происхождения зоны:

- `source` — `manual` или `osm`;
- `source_relation_id` — идентификатор OSM relation при импорте;
- `imported_at` — время импорта;
- `approved_by_user_id` и `approved_at` — кто подтвердил использование контура.

Критерий готовности: администратор импортирует или рисует район, подтверждает
его, а `by_service_area` детерминированно выбирает больницу по сохранённому
контуру даже при недоступности внешних картографических сервисов.

## Следующие функциональные этапы

### Геолокация и работа бригады

- [x] Добавлена серверная GPS-политика: настраиваемые интервал отправки,
  допустимая точность и срок свежести точки. Планшет получает её перед
  запуском фоновой задачи, а сервер отклоняет слишком частые и неточные точки.
- [x] Добавлен прогноз ETA для выбранной больницы и список активных прибытий
  для назначенных сотрудников больницы. В MVP расчёт использует Haversine,
  коэффициент дорожного пути и настраиваемую среднюю скорость; результат
  помечается свежестью исходной точки.
- интегрировать внешний сервис маршрутизации только после выбора поставщика и
  согласования требований к персональным данным и доступности сервиса;
- не заменять исторические координаты вызова текущими координатами устройства.

### Аналитика и аудит

- [x] Добавлен append-only журнал аудита и read-маршрут `GET /audit/events` с
  правом `analytics.read`. Уже журналируются изменения статусов ресурсов,
  расчёт/выбор направления больницы, публикация чеклистов, изменение ролей и
  `acces_status` учётных записей; запись события выполняется в одной транзакции
  с основной операцией.
- [x] Добавлены read-маршруты аналитика для завершённых вызовов, completed run,
  результата, выбранной больницы и сохранённых снимков кандидатов.
- определить срок хранения GPS-данных и журналов до появления реальных данных
  в production.

### Качество данных и UX API

- добавить пагинацию, сортировку и фильтры в списки;
- унифицировать ответы об ошибках и покрыть все `not found` корректным `404`;
- добавить E2E-сценарий от входа устройства до завершения вызова;
- [x] Добавлена идемпотентность device-запросов: `Idempotency-Key` защищает
  `POST`/`PUT`/`PATCH`/`DELETE` от повторного выполнения в пределах одной device-сессии;
  успешный или бизнес-ошибочный ответ повторяется в течение 24 часов.

## Отложенные security-задачи

Эти задачи не блокируют следующий функциональный этап, но обязательны до
реального production-запуска:

1. При каждом employee-запросе брать актуальные `acces_status` и роль из БД,
   а не полагаться только на claims ранее выданного JWT.
2. При блокировке пользователя и смене роли отзывать его refresh-сессии.
3. Запретить деактивацию или понижение последнего активного администратора.
4. Ввести аудит административных действий, ограничение частоты логина и
   production CORS allowlist вместо `*`.
5. Вынести секреты из локального `.env` в безопасное хранилище окружения
   deployment-платформы; не хранить их в Git, документации или логах.
