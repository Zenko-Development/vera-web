# Руководство пользователя Vera MVP

Этот документ описывает рабочие сценарии системы с точки зрения людей, а не
контракты HTTP. Точные URL, поля запросов и примеры ответов находятся в
[документации API](API_DOCUMENTATION.md).

## Что уже работает, а что пока в плане

В MVP уже можно:

- вести справочники больниц, типов учреждений и заболеваний;
- создавать чеклисты, их версии, вопросы, правила и варианты результата;
- выдавать планшету скорой постоянные учётные данные и открывать смену на
  выбранной машине;
- создать вызов, передавать геопозицию, пройти чеклист и получить результат;
- подобрать больницу по фиксированному правилу, типу учреждения или вручную
  заданной географической зоне.

Модули **операционных, медицинского оборудования и их рабочих статусов уже
реализованы**. Администратор создаёт справочники и физические ресурсы, назначает
сотрудника в больницу, а сотрудник поддерживает их актуальное состояние.

> Важно: административные маршруты защищены user JWT и правами роли. Перед
> первым запуском задайте `ADMIN_NAME` и `ADMIN_PASSWORD` в локальном `.env`:
> Go seed создаст первого администратора, если его ещё нет. Инструкция
> находится в [RBAC](RBAC.md). При изменении статуса ресурса сервер проверяет
> принадлежность сотрудника конкретной больнице.

## Участники и основные понятия

| Участник | Назначение |
| --- | --- |
| Администратор | Настраивает справочники, сотрудников, больницы, устройства и логику чеклистов. |
| Сотрудник больницы | Поддерживает актуальное состояние операционных и оборудования назначенной ему больницы. |
| Бригада скорой | Работает с планшетом: открывает смену на машине, ведёт вызов, проходит чеклист и получает направление. |
| Устройство (`device`) | Конкретный планшет. Это не сотрудник и не машина. Его идентификатор и секрет создаёт сервер один раз. |
| Машина (`ambulance_vehicle`) | Машина скорой с номером и статусом. На одну смену она связывается с планшетом через сессию доступа. |
| Вызов (`emergency call`) | Рабочий контекст конкретного выезда. Он принадлежит активной сессии планшета. |

В одном месте одновременно может быть только одна активная сессия у планшета
и одна у машины. У одной сессии одновременно допускается один активный вызов
и одно незавершённое прохождение чеклиста.

## Картина основного процесса

```text
Администратор
  ├─ создаёт больницы, зоны и опубликованный чеклист
  └─ создаёт машину и выдаёт планшету device_id + auth_secret

Бригада на планшете
  └─ выбирает номер машины → открывает смену
       └─ создаёт вызов → отправляет GPS → проходит чеклист
            └─ получает результат → подбирает / выбирает больницу
                 └─ завершает либо отменяет вызов → завершает смену
```

## 1. Работа администратора

### 1.1. Настройка ролей и сотрудников

Рекомендуемые роли для MVP:

- `administrator` — настройка системы и доступ ко всем справочникам;
- `hospital_operator` — сотрудник конкретной больницы;
- `analyst` — чтение журнала аудита через `GET /api/v1/audit/events` и
  завершённых вызовов через `GET /api/v1/analytics/emergency-calls`; для этих
  маршрутов необходимо право `analytics.read`.

Бригада скорой не создаётся как персональный пользователь: она работает от
имени планшета. Это намеренно позволяет не хранить личность каждого члена
бригады в потоке экстренного выезда.

Порядок создания сотрудника:

1. Создайте роль через `POST /api/v1/role/` и при необходимости добавьте ей
   разрешения через маршруты `/permission` и `/link/role/{role_id}/permission`.
2. Создайте учётную запись через `POST /api/v1/user/`. Нужны логин, имя,
   фамилия, пароль, `role_id` и `acces_status: true`.
3. Передайте сотруднику только его логин и первоначальный пароль. Сервер
   сохраняет пароль в bcrypt-хеше; пароль не возвращается в ответах.
4. При увольнении или временном отстранении отключите доступ через
   `PATCH /api/v1/user/status/{id}` с `acces_status: false`.

Эти действия доступны только роли с `rbac.manage` и `user.manage`.

### 1.2. Настройка больниц и справочников

До публикации чеклиста администратор заполняет данные, от которых зависит
маршрутизация:

1. Создайте типы учреждений: например, `TRAUMA`, `STROKE`, `GENERAL`.
   Сейчас тип учреждения используется как простой тег для выбора кандидатов.
2. Создайте больницы: название, адрес, тип учреждения, координаты и контакты.
   Координаты нужны для последующего отображения и проверки данных; текущая
   маршрутизация по зоне использует именно полигон зоны, а не расстояние до
   больницы.
3. Создайте заболевания и свяжите их с больницами, если эти данные нужны
   справочнику и интерфейсу.
4. Для режима «по зоне обслуживания» создайте у больницы одну или несколько
   зон через `POST /api/v1/hospital-service-areas/`. Граница — замкнутый
   полигон из точек `[latitude, longitude]`; задайте приоритет. Если точка
   находится в нескольких зонах, выбирается зона с большим приоритетом.

Границы зон вводятся и проверяются вручную в MVP. Это не интеграция с ФИАС и
не определение адреса пациента: решение строится по последней координате,
которую прислала бригада во время вызова.

### 1.3. Настройка ресурсов и сотрудников больницы

1. Создайте типы оборудования через `/api/v1/equipment/` и типы операционных
   через `/api/v1/operating-types/`.
2. Добавьте в больницу каждую физическую единицу оборудования и каждую
   операционную. `label` должен однозначно и понятно определять ресурс внутри
   этой больницы, например `КТ-01` или `Операционная №2`.
3. Выдайте роли сотрудника `hospital_resource.read` и
   `hospital_resource.change_status`.
4. Назначьте сотрудника в больницу через `POST /api/v1/hospital-staff/`.
   Один сотрудник может быть назначен в несколько учреждений.
5. Чтобы сотрудник видел ожидаемые машины, выдайте его роли
   `hospital_arrival.read`. Он будет видеть только прибытия в учреждения,
   к которым назначен через `hospital_staff`.

Право `hospital_resource.manage` оставьте администратору: оно позволяет менять
структуру ресурсов и состояние ресурсов любой больницы. Подробные тела запросов
приведены в [API ресурсов больниц](api/hospital-resources.md).

### 1.4. Добавление машин и выдача планшета

Сначала зарегистрируйте машину, затем подготовьте физический планшет.

1. Создайте машину через `POST /api/v1/ambulance-vehicles/`, указав
   `car_number`. Новая машина получает статус `active`.
2. Выполните provisioning планшета: `POST /api/v1/device/` без тела запроса.
   Сервер один раз вернёт `device_id` и `auth_secret`.
3. Сохраните оба значения в защищённом хранилище приложения на этом планшете
   (или передайте через MDM/одноразовый QR-код). Не помещайте их в URL, чат,
   скриншоты или журналы приложения.
4. Убедитесь, что в интерфейсе планшета секрет больше не спрашивается у
   бригады: приложение берёт его из защищённого хранилища. Бригада вводит
   только номер машины при открытии смены.

`device_id` принадлежит планшету постоянно. Машина не закреплена за ним:
сегодня тот же планшет может работать на одной машине, в другую смену — на
другой.

Если планшет утрачен, скомпрометирован или переустановлен, сбросьте секрет
маршрутом `POST /api/v1/device/{device_id}/auth-secret`. Новый секрет будет
показан один раз, а активная сессия устройства будет отозвана. Затем запишите
новые данные в планшет и откройте смену заново.

Статусы машины:

- `active` — её можно выбрать при открытии смены;
- `inactive` — временно недоступна;
- `maintenance` — находится на обслуживании.

Нельзя переименовать машину или перевести её в `inactive`/`maintenance`, пока
она участвует в активной смене. Сначала корректно завершите смену.

### 1.5. Создание и публикация чеклиста

Чеклист меняется только через новую версию. Бригада всегда начинает
прохождение по опубликованной версии, поэтому уже начатый вызов не изменится,
если администратор готовит следующую редакцию.

Порядок работы:

1. Создайте сущность чеклиста (`POST /api/v1/checklist/`) и привяжите её к
   заболеванию.
2. Создайте версию через `POST /api/v1/checklist/{checklist_id}/versions/`.
   Она всегда начинается как `draft`; номер версии назначает сервер.
3. Добавьте вопросы. Типы: `single`, `multiple`, `text`, `number`, `boolean`.
   Для `single` и `multiple` добавьте варианты ответов.
4. Создайте возможные результаты: краткий заголовок и сообщение для бригады.
5. Для каждого результата настройте один маршрут:

   | Режим | Настройка | Что увидит бригада |
   | --- | --- | --- |
   | `fixed` | Конкретная больница (`hospital_id`) | Больница назначается автоматически. |
   | `by_tag` | Тип учреждения (`facility_type_id`) | Список подходящих больниц; бригада выбирает одну. |
   | `by_service_area` | Зоны обслуживания больниц | По последней свежей GPS-точке автоматически выбирается больница, чья зона содержит точку. |

6. Создайте правила для версии. У правила есть результат и приоритет: большее
   значение приоритета выигрывает. Условия одного правила объединяются как
   «И»: каждое из них должно выполниться. Для числовых и текстовых ответов
   задаётся `value`; для вариантов — `option_id`.
7. Добавьте правило по умолчанию без условий с наименьшим приоритетом. Оно
   предотвращает ситуацию, когда чеклист пройден, но результат не найден.
8. Проверьте черновик на тестовом устройстве: обязательные вопросы, каждый
   вариант ответа, каждое правило, отсутствие кандидатов и ручной выбор.
9. Опубликуйте версию: `POST /api/v1/checklist-versions/{id}/publish`.
   Сервер архивирует прежнюю опубликованную версию того же чеклиста. Назад
   изменять опубликованную версию нельзя — для исправления создаётся новый
   черновик и публикуется следующая версия.

Перед публикацией `by_service_area` обязательно проверьте, что зоны реально
покрывают нужную территорию и что в планшетном приложении включена отправка
GPS. Без свежей координаты этот режим не сможет автоматически назначить
больницу.

## 2. Работа сотрудника больницы

### Сведения о больнице

Сотрудник больницы может поддерживать справочные сведения о своём учреждении:
название, адрес, телефон, тип учреждения и координаты. Для этого
администратор назначает права `hospital.read` и `hospital.manage`. Ограничения
«только своя больница» пока нет: до появления связи сотрудника с учреждением
право `hospital.manage` даёт доступ ко всем больницам.

При изменении адреса, контакта или координат:

1. Найдите больницу в списке `/api/v1/hospital/`.
2. Измените только подтверждённые значения через
   `PATCH /api/v1/hospital/{id}`.
3. Если поменялась территория обслуживания, согласуйте границу и приоритет с
   диспетчером, затем обновите соответствующую зону.
4. После изменения зоны проведите тест с контрольной GPS-точкой до того, как
   рассчитывать на автоматическое назначение бригадам.

### Операционные и оборудование

Администратор заранее назначает сотрудника в одну или несколько больниц и
выдаёт его роли права `hospital_resource.read` и
`hospital_resource.change_status`. После входа сотрудник:

1. получает оборудование через `GET /api/v1/hospitals/{hospital_id}/equipment`
   и операционные через `GET /api/v1/hospitals/{hospital_id}/operating-rooms`;
2. выбирает конкретный физический ресурс по его `label`;
3. отправляет новое состояние в `PATCH /api/v1/hospital-equipment/{id}/status`
   либо `PATCH /api/v1/hospital-operating-rooms/{id}/status`;
4. проверяет возвращённые `status`, `status_changed_at` и `updated_at`.

Используются состояния `available` (доступен), `busy` (занят) и `unavailable`
(неисправен, закрыт или временно недоступен). Сервер не доверяет выбранной во
фронтенде больнице: он получает `hospital_id` из ресурса и проверяет назначение
текущего сотрудника. Администратор указывает требования к оборудованию и
операционным в результате чеклиста; направление исключает больницы, где таких
доступных ресурсов недостаточно. Полный журнал изменений остаётся следующим
этапом.

### Ожидаемые прибытия скорой

Сотрудник с правом `hospital_arrival.read` открывает
`GET /api/v1/hospital-arrivals`. В списке видны только активные вызовы, где
выбрана больница сотрудника: номер машины, время последней GPS-точки,
расстояние и приблизительное время прибытия.

Поле `location_is_fresh` обязательно показывайте в интерфейсе. Если оно
`false`, ETA построен по устаревшей позиции и не является актуальным
прогнозом. Текущий ETA рассчитывается без учёта пробок и внешней навигации,
поэтому он помогает подготовить ресурс, но не заменяет связь с диспетчером.

## 3. Работа бригады скорой помощи

### Перед началом смены

Предпосылки: планшет уже подготовлен администратором, в приложении сохранены
`device_id` и `auth_secret`, а нужная машина существует и имеет статус
`active`.

1. Откройте экран «Начать смену».
2. Введите номер машины. Регистр и внешние пробелы не важны: сервер
   нормализует номер, например ` a123bc77 ` в `A123BC77`.
3. Приложение отправляет сохранённые данные планшета и номер машины на
   `POST /api/v1/device-access/login`.
4. После успешного входа приложение получает access и refresh токены. Бригада
   не копирует и не вводит их вручную.

Если машина не найдена, неактивна или уже занята другой активной сессией,
нельзя обходить ошибку повторными запросами. Нужно сверить номер, статус
машины и завершение предыдущей смены с диспетчером/администратором.

### Ведение вызова

Для каждого действия, которое изменяет данные, приложение создаёт UUID
`Idempotency-Key`. Если сеть пропала после отправки, оно повторяет **тот же**
запрос с тем же ключом и телом, а не создаёт новый вызов или новую GPS-точку.
Для следующего самостоятельного действия всегда нужен новый ключ.

1. Создайте вызов: `POST /api/v1/emergency-calls/`. Вызов становится `active`.
2. Перед началом фоновой передачи приложение читает
   `GET /api/v1/device/geo-tracking-policy`. Как можно раньше и затем по
   настроенному сервером интервалу передавайте координаты:
   `POST /api/v1/emergency-calls/{id}/locations`. Передаются широта,
   долгота, точность и время получения координаты устройством. Точку с
   точностью хуже лимита политика отклонит; не отправляйте точки чаще
   указанного интервала.
3. Выберите нужный опубликованный чеклист и начните его:
   `POST /api/v1/checklist-runs/` с `checklist_id` и `emergency_call_id`.
4. Получите форму (`GET /api/v1/checklist-runs/{id}/form`) и сохраняйте ответ
   на каждый вопрос. Повторная отправка ответа на один вопрос обновляет его,
   поэтому можно исправить ошибку до завершения.
5. Заполните все обязательные вопросы и завершите прохождение. В ответе
   появятся сохранённый результат правила, его заголовок и сообщение.

Не начинайте второй вызов или второе прохождение «на всякий случай»: сервер
защищает от этого, но повторные действия в интерфейсе только затруднят
восстановление. При перезапуске приложения сначала запросите активный вызов и
активное прохождение, затем продолжите уже существующую запись.

### Получение направления в больницу

После завершения чеклиста выполните
`POST /api/v1/emergency-calls/{id}/destination/resolve`. Решение будет
сохранено вместе со снимком кандидатов, поэтому позже можно понять, почему
система предложила именно такой вариант.

Дальнейшие действия зависят от режима результата:

- `fixed` — на экране сразу будет назначенная больница;
- `by_service_area` — система использует последнюю GPS-точку, полученную не
  более двух минут назад, и назначает больницу из подходящей зоны;
- `by_tag` — система покажет список кандидатов. Бригада выбирает одну из
  сохранённых кандидатур через
  `POST /api/v1/emergency-calls/{id}/destination/select`.

Если получено `no_candidates`, не выдумывайте направление и не закрывайте
вызов как успешно завершённый. Уточните решение через диспетчера: возможно,
не настроен тег/зона, координата устарела или для района нет подходящей
больницы. Для режима зоны сначала отправьте свежую геопозицию, затем повторите
расчёт.

После ручного выбора закройте вызов маршрутом
`POST /api/v1/emergency-calls/{id}/complete`. Если вызов не состоялся,
используйте `POST /api/v1/emergency-calls/{id}/cancel`. Выбор больницы нужно
сделать **до** закрытия вызова: для выбора требуется активный вызов.

После автоматического или ручного выбора больницы приложение показывает ETA
из `GET /api/v1/emergency-calls/{id}/arrival-estimate`. Это приблизительное
время: сервер использует последнюю GPS-точку, среднюю скорость `80` км/ч по
умолчанию и коэффициент дорожного пути. Перед отображением проверяйте
`location_is_fresh`; при `false` попросите бригаду восстановить GPS-связь, а
не воспринимайте прогноз как текущий.

### Завершение смены и восстановление после ошибки

В конце смены нажмите «Завершить смену». Приложение должно вызвать
`POST /api/v1/device-access/logout` с refresh-токеном. Это освобождает
планшет и машину для следующей смены.

Если access-токен истёк, приложение должно бесшумно использовать
`POST /api/v1/device-access/refresh`. Если это не помогло, откройте смену
заново. Не удаляйте данные приложения и не сбрасывайте секрет без причины:
администратор выдаёт новый секрет только при provisioning или явном сбросе.

## 4. Контрольный список перед реальной сменой

Администратор перед началом эксплуатации проверяет:

- опубликованный чеклист существует и содержит правило по умолчанию;
- все больницы и типы учреждений из правил существуют и активны по
  организационным правилам;
- для `by_service_area` настроены и проверены полигоны, а планшет умеет
  посылать координаты;
- машины имеют корректные статусы, а данные каждого планшета сохранены
  безопасно;
- Go seed выполнен, первый администратор создан, а его учётные данные хранятся
  безопасно.

Бригада перед выездом проверяет:

- открыта смена именно на нужной машине;
- геолокация включена, время устройства корректно, а точность GPS приемлема;
- для активного вызова регулярно отправляется позиция;
- политика GPS загружена приложением, а точность и интервал отправки ей
  соответствуют;
- приложение создаёт и сохраняет `Idempotency-Key` до получения ответа на
  каждое изменяющее действие;
- направление выбрано или согласовано с диспетчером до закрытия вызова.
