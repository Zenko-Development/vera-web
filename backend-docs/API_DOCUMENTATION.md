# Vera Backend API

Для сценариев работы людей по ролям — администратора, сотрудника больницы и
бригады скорой — смотрите [руководство пользователя](USER_MANUAL.md).

Документация API-маршрутов, зарегистрированных в текущем [cmd/api/main.go](../cmd/api/main.go). Для каждой ручки указаны `URL`, `Request`, `Response`, HTTP-статус и пример JSON либо отсутствие тела.

Маршруты взяты из `main.go`, поля запросов и ответов — из `internal/*/dto.go`, связи и ограничения данных — из [db/migrations](../db/migrations). Статусы, преобразования полей и особенности текущего поведения сверены с обработчиками, сервисами и SQL-репозиториями. Примеры составлены по коду; запросы к работающему серверу и БД не выполнялись.

## Адрес и запросы

Базовый URL: `http://localhost:<BACKEND_PORT>/api/v1`. Порт читается из переменной `BACKEND_PORT` в [config/config.go](../config/config.go). Например, при `BACKEND_PORT=8080` вход доступен по `http://localhost:8080/api/v1/auth/login`.

В разделах указаны полные пути относительно хоста, уже с `/api/v1`. Параметры в фигурных скобках заменяются значениями: `{id}` → UUID конкретной записи. Строковые параметры URL, например названия с пробелами, передаются с URL-кодированием. Завершающий `/` указан там, где он зарегистрирован в `main.go`.

Для тела JSON используйте заголовок:

```http
Content-Type: application/json
```

Если написано «тело отсутствует», отправлять `{}` не требуется. Значения идентификаторов, дат и названий в примерах условные: идентификаторы связанных сущностей нужно заменить на существующие. Пагинация и query-фильтры для описанных списков не реализованы; фильтрация, где она есть, задаётся сегментами URL.

## Авторизация

В текущем `main.go` `AuthMiddleware` временно отключён. Поэтому зарегистрированные API-маршруты пока не требуют заголовок `Authorization` и не проверяют роль. Это режим локального MVP; фронтенд не должен воспринимать его как окончательный security-контракт. `/auth/login`, `/auth/refresh`, `/auth/logout` обслуживают сотрудников, а `/device-access/*` — обезличенные планшеты скорой.

## Формат ответов

Обычно успешный JSON-ответ содержит `data`. Форму объекта или массива смотрите у конкретной ручки:

```json
{
  "data": {
    "id": "11111111-1111-4111-8111-111111111111"
  }
}
```

Обычная ошибка обработчика:

```json
{
  "message": "invalid json"
}
```

JSON-ответы обработчиков обычно имеют `Content-Type: application/json`. Некоторые операции возвращают `200 OK` или `204 No Content` без тела. Единого правила для DELETE и PATCH нет: точный статус указан для каждой ручки.

Обязательность полей и значения по умолчанию зависят от DTO и обработки запроса. `NOT NULL` в миграции сам по себе не означает проверку непустой строки в API. Пропущенное поле `bool` или `int32` может записаться как `false` или `0`, даже если DEFAULT в БД другой. PATCH также не всегда сохраняет пропущенные поля — это отмечено в описаниях.

В текущем коде встречаются ответы `500` при отсутствии записи, `200` без тела при ошибке и несколько JSON-объектов подряд из-за продолжения обработчика после записи ошибки. Конкретные случаи описаны рядом с соответствующими ручками.

## Swagger UI

### GET /swagger/*

**URL:** `GET /swagger/index.html` (маршрут зарегистрирован как `/swagger/*`, вне `/api/v1`).

**Request:** тело отсутствует.

**Response:** `200 OK`, HTML-страница Swagger UI; ресурсы интерфейса также обслуживаются под `/swagger/`.

В текущем дереве проекта нет сгенерированной Swagger-спецификации и её регистрации через импорт пакета `docs` в `main.go`. Поэтому наличие маршрута UI само по себе не обеспечивает загрузку описания API. Полный список зарегистрированных ручек приведён в Markdown-разделах выше.

## Что не имеет HTTP-маршрута

Наличие DTO, таблицы или метода сервиса не означает наличие доступной ручки. В частности, сейчас не зарегистрированы отдельные маршруты `/session`, приём GPS-координат и поиск больницы для бригады. Они будут добавлены следующими модулями.

`GET /api/v1/checklist-questions/checklist-versions/{id}` вызывает получение одного вопроса по ID; список вопросов версии по этому URL недоступен. Маршруты публикации/архивации версии и CRUD условий правил уже зарегистрированы и описаны в соответствующих разделах.
